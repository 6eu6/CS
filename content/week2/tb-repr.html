repr(): seeing exactly what's inside a value

45 min5 scenarios · 8 predictions · 6 exercises

print() shows you a value the way a user should see it. repr() shows it the way a programmer needs to see it: with quotes, hidden spaces, tabs and line breaks made visible. Half of all "it looks right but doesn't work" bugs are found in seconds with repr.

The question it answers

"What exactly is inside this variable?" Not what it looks like when printed. What it really is.

The name

repr is short for representation. It returns a string that represents the value as Python source code would write it. For most simple values, if you typed repr's output into Python, you'd get the same value back.

The problem it solves, in one example

A user typed their name into a form. You compare it and it fails. You print it to check:

name = "Sara "             # imagine this came from input(), with a stray space
print(name)                # Sara       ← looks perfect
print(name == "Sara")      # False      ← but why?!
print(repr(name))          # 'Sara '    ← there it is: a space before the closing quote

print can't show you a trailing space: it's invisible. repr wraps the value in quotes, so you can see exactly where the text starts and ends.

Why containers already use repr

When you print a list, Python shows each item with repr, not str. That's why print(["Sara "]) shows ['Sara '] with the space visible. Python's designers chose this because a list of strings printed with str would be ambiguous: [a, b] could be two names or two strings.

Try it

Three ways to get a repr

name = "Sara "
print(repr(name))         # 'Sara '   1. the function
print(f"{name!r}")        # 'Sara '   2. !r inside an f-string: "use repr for this one"
print(f"[{name}]")        # [Sara ]   3. the poor man's version: brackets around it

In real Python 3.8 or newer there's a fourth, beloved by professionals: print(f"{name=}") prints name='Sara ', the variable's name and its repr. It's the fastest debug print there is. (The in-browser engine on this site doesn't support = in f-strings, so try that one in your Codespace.)

Real-work scenarios

Scenario 1: "The login says the email doesn't exist, but it does"

You work on a booking system. A customer swears they registered. Your lookup fails.

registered = ["sara@nhs.net", "omar@ucl.ac.uk"]
typed = "Sara@nhs.net\n"          # pasted from an email, with a line break

print(typed in registered)        # False
print(repr(typed))                # 'Sara@nhs.net\n'   ← capital S and a \n
clean = typed.strip().lower()
print(clean in registered)        # True

Why repr is the right tool: printing typed shows a perfectly normal email. Only repr reveals the capital letter and the invisible \n. In real jobs, the first thing a senior developer asks when a comparison "mysteriously" fails is: "what's the repr?"

Scenario 2: Writing log messages that can be trusted

Production systems write logs: lines describing what happened, read later when something breaks. Compare:

user = ""
print(f"Login attempt by {user}")       # Login attempt by          ← was it empty? spaces? nothing?
print(f"Login attempt by {user!r}")     # Login attempt by ''       ← clearly an empty string

Professional habit: in log and error messages, put user-supplied values in !r. Python itself does this: KeyError: 'juice' and invalid literal for int() with base 10: 'abc' both use repr, so you can see exactly what the bad value was.

Scenario 3: Cleaning data imported from a spreadsheet

row = "Sara,  42 ,London\t"
for field in row.split(","):
    print(repr(field))
# 'Sara'
# '  42 '      ← spaces around the number
# 'London\t'   ← a tab glued to the city

Before you clean data, you need to see its mess. Looping over fields with repr is the first step of almost every data-cleaning job. After seeing it, you know you need .strip() on every field.

Scenario 4: "The number won't add up"

price = input("Price: ")    # user types 4.50
qty = 2
print(price * qty)          # 4.504.50    ← string repetition, not maths
print(repr(price))          # '4.50'      ← quotes: it's text
print(type(price))          # <class 'str'>

repr and type() together answer "what is this really?" in two lines.

Scenario 5: Your own objects (preview of Week 8)

class Book:
    def __init__(self, title):
        self.title = title
    def __repr__(self):
        return f"Book({self.title!r})"

print([Book("Dune"), Book("Emma")])     # [Book('Dune'), Book('Emma')]

When you write classes, you define __repr__ so your objects print usefully in lists, logs and error messages. Without it you'd see something like <__main__.Book object at 0x10f3>. Week 8 covers this properly; for now, know that repr is a protocol: every type can decide how it represents itself.

Use it well

  • Debugging: when a comparison or lookup fails, print the repr of both sides.
  • Logs and error messages: use !r for values that came from users or files.
  • Never show repr to end users. Customers should see Hello, Sara, not Hello, 'Sara'. str is for users, repr is for developers.
  • Don't parse repr output. It's for reading, not for storing data. To save data, use CSV (Week 6) or JSON.
  • Floats: in real Python, repr(0.1 + 0.2) is 0.30000000000000004, the exact stored value, while formatting hides it. (This site's engine rounds float repr, so try that one in your Codespace.)
